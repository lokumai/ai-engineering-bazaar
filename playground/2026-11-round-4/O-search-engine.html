What should search run on, with no server?

Milestone M56, issue #43. The site is static files on GitHub Pages, so search runs in the reader's browser, on an index built when the site is built. Every number below was measured on this repository's own corpus (the 19 written modules, in English, Turkish and Persian), not quoted from documentation. The placement of search is on page N; any placement there can sit on any engine here.

Decisions for you on this page

  1. The engine. One of O1 to O4. Recommended: O1 now (a build-time index with MiniSearch and our own small text normaliser, loaded the first time the field is focused), built so that O4's semantic layer can be added later as an opt-in.
  2. The default scope. Search the reader's own track and language by default, or everything. This costs nothing in the engine either way: one index per language is loaded, and a second only when the reader asks for it. Page N lets you try both. Recommended: own track and language.
  3. Unwritten For Everyone modules. Leave them out of the index, so no result opens a page that says "not written yet". Recommended: leave them out. Today none of the For Everyone modules is written, so this leaves the index unchanged; the build then includes a module the day its file exists.
  4. Semantic search. Whether to offer it at all, given its download (O3 and O4 give the sizes). Recommended: not in the first version; keep the door open.

Write back the codes, for example "O1, own track and language, unwritten left out, no semantic yet".

How this was measured

Scripts in a scratch folder outside the repository (nothing was installed into it). Machine: 13th Gen Intel Core i7-13620H, 16 threads, Node 22.16, Google Chrome 157 driven by Playwright, files served from a local server with gzip on for JavaScript, JSON and WebAssembly (as GitHub Pages does for those types) and no throttled network. Libraries: MiniSearch 7.2.0, FlexSearch 0.8.212, Lunr 2.3.9, Pagefind 1.6.0, Transformers.js 4.3.2 (ONNX Runtime Web 1.31). The site export came from npm run build in this worktree: 46.8 seconds, 1.75 GB of memory at its peak (that build exists today whatever search is chosen).

  • Sizes are bytes of the file a browser would download. "gz" is gzip level 9 (the one GitHub Pages applies). Pagefind and the model files are not compressible by the server, so their raw size is the download.
  • Query times come from 50 queries drawn from the corpus (whole words, four-letter beginnings, in each language), run in Chrome after the index is loaded. "4x" means Chrome with its CPU slowed four times, a stand-in for a mid-range phone, not a phone (see "Not measured").
  • Turkish and Persian handling is a test on 25 words per language drawn from the corpus itself (words that appear in at least three modules, with ı ğ ş ç ö ü in Turkish and a zero-width non-joiner in Persian), each typed four ways. A word passes when the search returns at least one module that contains it. The recall column is the average share of those modules returned.
  • Meaning queries are 16 questions per language written without the module's own title words (for example "how do I stop users from tricking the model into bad answers" for Security), each with the modules a reader would be right to land on. One person labelled them (me, from the module summaries), so read the result as a direction, not a score.

O1

A build-time index and a small client library

Recommended

A script reads the markdown at build time and writes one index file per language. The browser downloads the library and the index the first time the field is focused, and searches in memory. Three libraries were tried on the same sections: MiniSearch, FlexSearch and Lunr.

  • The smallest download of the real options: 64 to 88 KB of index per language plus a 6 KB library (MiniSearch), and a query takes a fraction of a millisecond.
  • Fields are searchable on their own, so the "titles, prose, code" scope of page N is a query option (tested: for "memory", MiniSearch returns 53 sections over all three fields, 6 for headings only, 44 for prose only and 10 for code only).
  • None of the three handles Turkish or Persian text correctly as shipped (see the tables). A text normaliser of about 25 lines, applied to the index and to the query, fixed every case tested. We own that code.
  • Snippets need the text. Storing it costs another 88 to 109 KB (gzip) per language, loaded with the index or fetched per module.

Why recommended: it is the cheapest to load, has no build tool beyond a short script, and it is the only option here where Turkish and Persian are fully in our hands. The cost is that we write and test the normaliser, and the ranking is ours to tune.

When it loads

On the first focus of the field, never on page load: the library (5.9 KB gzip) and the language's index. Measured first-focus download: English 72.8 KB, Turkish 96.4 KB, Persian 89.2 KB. The index is read into memory in 12 to 21 ms on this machine, 41 to 60 ms with the CPU slowed four times. The first query takes 2 ms (6 to 9 ms slowed).

Cost to build

Indexing one language takes 29 to 36 ms. A script of about 60 lines reads curriculum.yaml and the written modules, and writes three JSON files. One dependency, 6 KB in the browser.

* A word typed with a space becomes two short words, and an engine that matches any of them returns the module; this counts that as found, and says nothing about the order of the results. Lunr's trimmer treats every character outside A to Z as a non-word character and strips it from the ends of a word: tested directly, it turns the Persian word "می" into nothing and the Turkish "şimdi" into "imdi", so Lunr finds no Persian word as shipped. FlexSearch with our normaliser returns fewer modules for the spaced form because it requires both halves to match.

What the normaliser does, per language. Turkish: lower-case with the Turkish rules (I to ı, İ to i), then fold ı ğ ş ç ö ü â î û to their plain letters, so a reader on an English keyboard finds "görev" by typing "gorev". Persian: replace Arabic yeh and kaf with the Persian forms, remove the zero-width non-joiner, the short-vowel marks and the stretching mark, and turn Persian digits into ASCII ones. English: lower-case.

O2

Pagefind, built from the static export

Pagefind reads the built HTML pages after the export, writes a set of small index chunks, and its own JavaScript and WebAssembly download only the chunks a query needs. It also stores a short text fragment per page for the snippet and highlights.

  • Almost no code of our own: one command after npm run build. It returns snippets with the match marked, and sections of a page (6 sections for the first hit in the English test).
  • Its Persian handling is partial (see the table): Arabic yeh and kaf failed on 14 of 25 words, and a ZWNJ typed as a space returned only 74% of the right modules. Turkish ASCII spelling found 22 of 25 words.
  • It searches one body of text per page. Limiting a query to titles or to code, which page N offers, is not an option it has; a separate small titles index would be needed, and code could only be left out (not tested).
  • The exported Persian pages declare <html lang="en"> (measured), so Pagefind would file them under English. The numbers here come from running it once per language with --force-language; the real build would either run it that way or set the page's language.

When it loads

On first use, from Pagefind's own script: its JavaScript (13.4 KB gzip), a worker (12.4 KB gzip), a WebAssembly file (55 to 60 KB), a small header and the one index chunk the query touches. Measured for one query: English 118.6 KB, Turkish 125.5 KB, Persian 116.0 KB before any result text, and about 7 to 10 KB more for each result's fragment. First query, in Chrome, import and search together: 94, 92 and 99 ms. Warm queries take 0.4 to 0.5 ms.

Cost to build

0.09 to 0.14 seconds per language, after the 46.8-second export that exists today. One dependency (a 13 MB platform binary, used only at build time). The index covers 46 English pages (everything under /courses/, drafts included) and 19 pages each in Turkish and Persian.

O3

Semantic search: embeddings at build time, a model in the browser

At build time every section is turned into a vector (a list of 384 numbers) by a model; the vectors ship as a file. In the browser the same model turns the reader's question into a vector and the page finds the nearest sections. Two models were run, both quantised to 8 bits: all-MiniLM-L6-v2 (English only) and multilingual-e5-small (100 languages, including Turkish and Persian).

  • It finds what the reader means, not only the words: "how do I stop users from tricking the model into bad answers" lands on Security. On the 16 meaning queries it put the right module in the top three 13, 9 and 11 times (English, Turkish, Persian), against 9, 9 and 9 for keyword search. An English question also found the right Persian module in the top three 12 times of 16.
  • The download is the cost, and it is large: 129.3 MB for the multilingual model on first use, 30.2 MB for the English-only one (and that one found the right Turkish module 4 times of 16 and the Persian 3).
  • It does not find an exact word as well as it finds a meaning, and it cannot highlight a match. Titles typed as queries were found as well by both (19 of 19 each).

When it loads

Only on demand, never on page load: the model and its runtime on the first semantic query, the vectors with them. Fetched in Chrome (gzip where the server applies it): multilingual-e5-small 129,329,399 bytes in all (model 118,308,185, tokenizer 3,984,739, ONNX Runtime WebAssembly 6,690,348, Transformers.js 171,573, vectors 155,136). MiniLM: 30,217,258 bytes (model 22,972,370).

Time to load and run, on this machine, files from a local server so no network time: model ready in 2.2 s (MiniLM 1.2 s), first query 60 ms (50 ms), later queries 17 ms (7 ms). With the CPU slowed four times: ready in 5.6 s (2.8 s), first query 208 ms (161 ms), later queries 67 ms (30 ms). The download then dominates: 129.3 MB takes about 103 seconds at 10 Mbit/s and about 21 seconds at 50 Mbit/s (30.2 MB takes 24 and 5 seconds).

Cost to build

Embedding the sections takes 7.3, 7.9 and 9.1 s for English, Turkish and Persian with the multilingual model (18 to 23 ms per chunk, on 16 cores), plus a 118 MB model download in CI, which can be cached. Chunks are at most 900 characters: 404 English, 427 Turkish, 401 Persian.

The keyword method here has to read a whole sentence, which it does poorly by design (it matches any word). A reader who types one or two words, the usual case for module and level names, does as well with either: all 19 module titles typed as queries came first for both. The questions are in queries.mjs in the scratch folder, one labeller, 16 per language: a direction, not a benchmark.

Hosting the model: GitHub Pages sites may be up to 1 GB, but git refuses a single file over 100 MB and the e5 model is 118.3 MB. A site deployed from CI as an artifact may not hit that limit, and the alternative is to let the browser fetch the model from Hugging Face's servers, which is what Transformers.js does by default and which makes every semantic search a request to a third party. Neither was tested.

O4

Hybrid: keyword first, the semantic layer on demand

O1 answers every query. A reader who wants more presses one button under the results ("Search by meaning", with its size stated); only then is the model downloaded, once, and kept by the browser. The semantic results are merged with the keyword ones by rank.

  • The everyday search stays as light as O1: 73 to 96 KB on first focus.
  • Merging helped where keyword alone was weakest: top-three hits on the meaning questions were 13, 9 and 13 (English, Turkish, Persian), against 9, 9 and 9 for keyword alone and 13, 9 and 11 for semantic alone.
  • The cost is complexity: two engines, a merge rule, a download prompt, and two sets of files to build and keep in step. The 129 MB download is for readers who ask for it.

Why not first: on this corpus the gain is on long questions, not on names or single words, and the corpus has 19 written modules today. Keyword search with our normaliser answers the author's stated need (module and level names and their content). O4 can be added later without changing O1: the keyword index stays as is.

When it loads

Keyword part on the first focus, as O1. Semantic part only when the reader presses the button (or never). Sizes and times as O3: 129.3 MB, ready in 2.2 s (5.6 s slowed), 17 ms per later query (67 ms slowed).

Turkish and Persian

The keyword part uses our normaliser (all cases tested pass). The multilingual model needs no normaliser: it handles the Turkish and Persian letters itself.

Cost to build

O1's script, plus O3's embedding step: 7 to 9 s per language and a 118 MB model in CI.

Recommendation: O1 now. It loads least, answers fastest, is exact on every Turkish and Persian case tested, and supports the scopes page N draws. Keep its index and its snippet text separate from the engine so that O4's semantic layer can be added later, on request, if you decide the 129 MB opt-in is worth it. O2 is the choice if you would rather own no search code at all and accept its Persian gaps (Arabic-letter queries, spaced ZWNJ) and the missing scopes.

What could not be measured

  • A real phone. There is no phone in this setup. "Slowed four times" is Chrome's CPU throttle on the main thread, which does not slow Pagefind's worker, so no slowed figure is given for Pagefind. A semantic first query on a mid-range phone is therefore not measured; the load and query times above are a lower bound.
  • Download time on a real network. The files were served locally, so only sizes were measured. The seconds given for the model are arithmetic from its size at 10 and 50 Mbit/s.
  • Multi-threaded WebAssembly. It needs two response headers that GitHub Pages cannot set, so the semantic timings are single-threaded, which is what the real site would get.
  • Hosting the 118 MB model on GitHub Pages or from a third party, as noted under O3.
  • Search quality beyond the 16 questions per language, and Pagefind and Lunr on those questions. Ranking was not tuned for any engine.
  • The For Everyone modules: none is written, so an index of them was not measured. The sizes above are the For Engineers track; a written For Everyone track adds its own index per language, built the same way.
